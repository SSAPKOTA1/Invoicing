# Decisions

1. Repo root is the project root; the Python package is `supplier_app/`. The environment fixed the working branch `claude/zen-cannon-x8l4cj` instead of `build/initial`.
2. Dev venv at `.venv` (ignored). Local Python is 3.13, CI targets 3.11; code stays 3.11-compatible.
3. Ledger entries carry both `entry_type` (incl. `REVERSAL`) and `category_type` (economic type; for reversals the type of the reversed entry) so SQL aggregates and the pure engine need no joins.
4. Notice claims are cumulative per invoice (principal / fees / interest / flat fee / other costs). Booking posts only the delta against charges already in the ledger, which prevents double counting when later letters restate earlier fees.
5. Unapplied payment money is a PAYMENT ledger entry with `invoice_id = NULL` (credit on account of the supplier).
6. Interest: days counted for `due < d <= until`; a payment on day P reduces the principal from P+1. Interest rounded once (ROUND_HALF_UP). Seeded base rates are defaults to verify, not legal advice.
7. Money is integer cents; VAT rate is stored as text decimal; interest rate as `Decimal`.
8. Extra column `flat_fee_cents` on notices (Verzugspauschale) in addition to the fields in the brief.
9. Recognition is review-first: every imported document gets status `pending` (or `needs_review` when confidence < 0.75 or errors exist); bookings only happen in `IngestService.confirm`.
10. Collection letters that print a total before deducting payments ("Gesamtforderung" + "abzüglich Zahlung" + "Noch zu zahlen") are mapped to claim total = remaining amount and principal = principal − paid, so reconciliation compares like with like.
11. Court costs are booked as `COLLECTION_COST` (no separate ledger type); `ReferenceType` labels are matched case-insensitively and tolerate one OCR-inserted space inside compound words.
12. Modules named `types.py` were avoided (they shadow the stdlib when a script runs inside the folder): `result_types.py`, `ledger_types.py`.
13. The synthetic fixtures use only invented companies; IBANs are public example IBANs with valid checksums.
14. Dashboard definitions: "open payables" = sum of positive invoice balances (= aging total); credits (overpaid invoices + unassigned payments) are reported separately, so open − credits = sum of supplier ledger balances = sum of all ledger entries.
15. Dashboard default period is "this year"; KPIs "due in 7/14/30 days" have no previous-period value; the discrepancy KPI is the sum of absolute claimed-vs-ledger differences of notices in the period.
16. Qt combo boxes return str-enums as plain strings; screens convert them back (`PaymentMethod(...)`, ...). UI tests patch modal dialogs and tear Qt down explicitly (`tests/conftest.py`).
17. Domain texts produced by services (reconciliation messages) are German literals; every UI label lives in `i18n/de.json` (a test checks that all `tr()` keys exist).
18. PIN recovery: `SupplierApp.exe --reset-pin` after typing a confirmation phrase; the PIN is a screen lock, the data is not encrypted.
19. Companies/hotels (migration 004): `companies`, `hotels`; nullable `company_id`/`hotel_id` on invoices, payments, documents. A hotel implies its company (service validation plus DB triggers); a company alone is allowed. Scope filtering is done in SQL by joining invoices/payments, so every aggregate (dashboard, aging, statements, reports) uses the same code path.
20. Scope semantics: hotel view = that hotel only; company view = the company incl. all its hotels and company-level items; "all" = everything. Documents without assignment stay visible in every view (otherwise freshly imported scans would vanish). Unapplied payment credit uses the payment's own scope (explicit, or inferred from the paid invoices).
21. The scope is a single global selector in the header (persisted in settings, falls back to "all" if the entry was deleted) instead of per-page filters, so all layers always agree; each page shows the active scope as a badge.
22. Due date: the review form has an explicit "Fälligkeitsdatum" field; a missing date is proposed as invoice date + default payment days and flagged as low confidence. Later edits go through services (`change_due_date`, `update_deadline`, `assign_scope`) and are audited and written to the case timeline; the ledger is not touched (interest is derived from the due date at calculation time).
23. Printing uses Qt (`QPrinter`, `QTextDocument`) with a shared renderer for printer, preview and PDF, so what the preview shows is what is printed; the existing reportlab PDF export remains for file export.
24. Invoice recognition (net/vat/gross): every amount with a recognised label is a candidate (line label, table header over a value row, stacked/alternating label-value lines from PDF text layers, summary rows with three amounts); the combination with `net + vat = gross` wins, a labelled-less consistent triple in the text is used as fallback, and missing values are derived and marked (`derived`, confidence < threshold, validation hint). Printed values that do not add up are kept and reported instead of being "corrected" silently.
25. Vocabulary lives in `ai/vocab.py` (DE/EN/FR/IT/ES/NL) as data; users add words per field in Settings (`custom_vocab`, JSON) and they take precedence. Weak labels (`Summe`, `Total`, `Gesamt`) only count at the start of a line; Skonto/Rabatt/Anzahlung lines are never totals; offers/orders are down-weighted so they are not classified as invoices.
26. Credit-note amounts are returned as positive values (the ledger books the credit with its own sign); several invoice numbers are ordered by label strength so "Gutschrift-Nr." wins over "zu Rechnung …".
27. Multi-user = PostgreSQL server (psycopg 3), not SQLite on a share (SQLite WAL does not work over network file systems). Local single-user mode stays the default and needs no server. The repositories are shared: SQL is written once with `?` placeholders in a portable subset; `PgDatabase` translates (`?`->`%s`, `LIKE`->`ILIKE`, `RETURNING id`, numeric sums -> int) and exposes the `Database` interface. Migrations are written in SQLite dialect and translated for PostgreSQL (identity columns, BIGINT, BYTEA); triggers (append-only ledger, hotel/company consistency), search (GIN index over `fts_norm(...)`) and the change counter are PostgreSQL-specific `PG_EXTRA` statements.
28. Concurrency: every top-level transaction takes a global advisory lock (like SQLite's BEGIN IMMEDIATE) and every mutating service operation is wrapped in it from the first read (`@atomic`), so balances/allocations/duplicate checks cannot be overtaken (a test shows six simultaneous full payments of one invoice would otherwise overpay it by 5,000 EUR). Inside a transaction each write runs in a savepoint so a rejected insert does not poison the transaction (SQLite semantics the repositories rely on).
29. Users: `app_users` (scrypt hash + salt, roles admin/editor/viewer, lockout after 5 failures, last administrator protected). The viewer role is enforced in the database layer (every write statement is refused), not only in the UI. Audit entries carry the user name. The PIN lock is replaced by the user password in multi-user mode; personal settings (theme, scope, dashboard period, Tesseract path) are kept in a local `prefs.json`.
30. Live refresh: statement-level triggers bump `data_version` (with `changed_by`); the client polls it every 3 s and refreshes all screens when a colleague changed something (own changes do not trigger a second refresh). Document files are stored in `document_files` (BYTEA) with a local cache folder; backups of the server are table dumps (JSON lines in a zip) that are restored with TRUNCATE + reload; a local installation is transferred with the same loader.
31. Shared-folder mode (multi-user without a server, requested explicitly): the same SQLite file in a shared folder, but with the rollback journal (`journal_mode=DELETE`, WAL does not work on network shares), `synchronous=FULL` and a 30 s lock wait; writers are serialised by SQLite's `BEGIN IMMEDIATE` plus the `@atomic` service operations, so the concurrency guarantees are the same as on the server (tested with threads and with separate processes). Documents stay as files in the shared folder; logs, exports, connection settings and preferences stay on each PC (`AppPaths.local`). Risk management instead of a promise: quick_check on every start, a consistent daily copy in `backups/auto` (14 days), refusal of cloud-synchronised folders, heartbeat files (`sessions/`) that show who is connected and block restoring a backup while others work, `data_version` + `changed_by` for live refresh. The documentation states the limits (SMB only, few users, a dropped connection mid-write can still damage the file).
32. English interface: `i18n/en.json` has exactly the keys of `de.json` (placeholders identical, enforced by a test); the language is a per-PC preference (`prefs.json`, key `language`, read before the database is opened so that even the first dialogs are translated) and takes effect at the next start - switching live would mix both languages on screen. `--language en` overrides it for one run (screenshots, tests).
33. Texts that the program code produces itself stay German in the code and are translated by `tx()` using the catalogue `i18n/messages.py` (German text with `{name}` placeholders -> English text). `SupplierAppError` translates its message and hint when it is created, so every error is covered at one place; dashboard, report, history and warning objects translate their titles/headings when they are built. Booking descriptions are stored in German (one canonical language in a shared database) and translated only when shown, so colleagues with different languages see the same data. A test reads all `XyzError("...")` calls from the source and fails when one has no English text; a second test opens every screen, dialog, drill-down, report and history in English and fails when German function words are left.
34. Number, date and money formats stay European (`1.234,56 €`, `31.12.2024`) in both languages: the amount parser accepts German input and switching decimal separators with the language would make typed amounts ambiguous (`1.234`). Demo data and the sample letters stay German because they are test documents for the (multilingual) recognition.
35. Supplier recognition returns ranked candidates with evidence (IBAN, VAT id, tax number, e-mail domain, name in letterhead / sender line / footer / text, creditor of a mandate, known references) that are combined as a noisy OR, so one strong hint or several weak hints are enough while two equally good suppliers lower the certainty. Own companies/hotels (plus names from the settings) are excluded from the author search. Name similarity is token based and IDF weighted (generic words such as "Hotel" or "Service" count little).
36. A letter that restates a creditor (collection agency) keeps the agency as author and the creditor as supplier; mandate lines are not searched for the author. Names printed in the body count only 0.2 when a clearly different letterhead exists.
37. Reference extraction is label driven (four layouts); a value must contain a digit and must not be a date or an amount; it ends at the next label, `vom <date>` or a double space. A test corpus (`tests/recognition_corpus.py`, 72 generated letters incl. OCR noise and look-alike master data) measures accuracy; thresholds are asserted in `tests/test_recognition_accuracy.py` (clean: supplier >= 98 %, references >= 95 %; noisy: supplier >= 90 %).
38. Documents without an invoice: `confirm()` raises `AssignmentMissingError` (a `ValidationError` subclass); the UI shows a warning and calls `confirm(..., allow_unassigned=True)`, which files the document under the supplier with `assignment_pending=1` and the user's proposal as JSON; nothing is booked. `pending_review()` + `confirm()` books it later. Migration 006 also rebuilds `document_references` (CHECK list gained contract_number / letter_number).
39. The ledger stays append-only, so "change supplier" of an invoice is a reversal under the old supplier plus a new INVOICE entry under the new one (both dated with the invoice date so every as-of report nets to zero for the old supplier). It is refused while payments, credit notes, write-offs or letters exist for the invoice or the new supplier already uses the number. Changing the sender of a letter only changes the master-data link (it must be the letter's supplier or one of its agencies).
40. Recurring invoices (migration 007) are templates (`recurring_invoices` with effective-dated `recurring_amounts`); `recurring_runs (recurring_id, occurrence)` is unique, so a period can only be generated once even with several PCs. Generation runs at start-up and hourly (viewer role never generates), catches up all missed periods (max 60 per template and run), and adopts an existing invoice with the same supplier and number instead of creating a duplicate. Number patterns use `{prefix} {year} {month} {quarter} {half}` and are validated to change from period to period.
41. Bank statements (migration 008): `bank_accounts` (own accounts with company/hotel), `bank_statements` (file hash is unique), `bank_transactions` (fingerprint is unique). The fingerprint is the account, booking date, amount, counterparty IBAN and name and the purpose reduced to letters and digits, plus a running number for identical lines within one file; so overlapping statements and the same statement in another format do not create duplicates, while two equal payments on one day are both kept. Reference numbers are not part of the fingerprint because formats print them differently.
42. Matching evidence for a bank transaction: IBAN of the supplier (0.95) or of an earlier payment (0.85), name similarity (0.55-0.9), open invoice number in the purpose (0.85; short pure digits 0.45), known reference (0.7), equal amount (0.3), recurring payment (0.4). Invoice proposal: invoice numbers in the purpose, else the single open invoice with that balance, else a subset of at most five of the 14 oldest open invoices that sums to the amount. A transaction is "matched" only when the proposal adds up exactly and the certainty is >= 0.7; "book certain matches" books those >= 0.85. Incoming money and transfers between own accounts are ignored; incoming money is never booked as a supplier payment. Booking uses the normal payment service (allocation rule, scope of the paid invoices, otherwise of the account), learns IBAN and alias, and refuses a probable duplicate unless confirmed. Reversing the payment releases the transaction.
43. PDF statements are best effort (lines "date ... amount S/H"); the result always carries a warning to check. Bank files dropped on the documents page are routed to the bank page (non-PDF files that look like CSV/CAMT/MT940).
